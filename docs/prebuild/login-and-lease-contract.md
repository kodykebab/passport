# Login and renewable lease contract — current iteration

Keep existing code/PKCE routes and ID-token-only responses. Use EdDSA restricted to Ed25519, purpose-specific token types and key IDs. Publish discovery and issuer public JWKS. Never trust token-supplied key URLs.

Manually provision a separate site private key and issuer-held public key. Bind short-lived client assertions to the exact endpoint and request body; reject replay. Keep demo password login (`amr=["pwd"]`), seeded users and existing identity links. No automatic site-user creation or email linking.

Existing issuer users may also use [email-code login](email-login-contract.md). ID tokens distinguish password (`amr=["pwd"]`, `passport_auth_method="password"`) from email code (`amr=["otp"]`, `passport_auth_method="email_code"`). Clients require a matching pair. Both methods use the same code/PKCE exchange and native session/lease rules; account mutations still require a fresh password.

Durable issuer login records bind subject, client and issuer native browser session. Durable client federation records bind protocol login to native session, identity association ID and access epoch. The site generates a fresh opaque epoch when an association is created or its issuer, subject or user changes. Restoring the previous field values does not restore the old epoch. Native session creation and renewal validate that binding under the association row lock; renewal releases all locks before contacting the issuer and rechecks afterward. A lease expires no later than issuance + 300 seconds or either absolute deadline. Renewal validates authoritative issuer session/account and local native session/user/identity. Renewal never changes last activity or authentication time. Local logout, disablement and unlink/relink cannot be undone by delayed responses. Missing federation context or association binding fails closed.

Client schema migration adds the hidden access epoch to existing identity records; the existing after-migrate installer initializes only missing epochs. Repeating migration preserves existing epochs and links. Existing federation sessions without an association binding require a fresh federated login. Do not backfill them from the current identity: the earlier association may have been revoked. Independent native sessions and local application permissions remain unchanged. Deploy schema and client code together with normal site maintenance; run migration before serving requests. Direct SQL identity edits bypass document validation and are outside the supported mutation path.

The isolated admission candidate adds a hidden `admitted` field, default false. Approval changes require System Manager authority, including when a caller uses `ignore_permissions`, and rotate the association epoch. Binding changes clear approval. Native document history records ordinary saved changes when version tracking is not explicitly suppressed. One `admission_policy` SQL record controls compatibility or enforced admission. Missing or unknown policy denies Passport authority. Final session insertion, session validation and renewal use the shared association check; enforced mode also requires approval. Fresh installation initializes enforced mode. The upgrade patch initializes compatibility once and refuses to recreate a deleted policy after its Patch Log entry exists.

The internal activation operation requires System Manager authority and a complete reviewed association-to-epoch map. It locks identities before the policy row, rejects a changed review, saves selected approvals with native history, rotates remaining epochs, and records enforcement plus actor, time and a request digest in the same transaction. Repeating the same completed activation does not change grants. The caller owns commit or rollback; activation performs no network call or internal commit. These functions have no public HTTP endpoint or UI. Mixed-version deployment, additional concurrent writers and production workload bounds remain release gates; this candidate is not promoted for live use.

Lease expiry blocks protected HTTP and realtime without deleting an otherwise-live native session. Explicit renewal can resume access only after authoritative validation; outage time does not pause idle or absolute expiry. Never automatically replay interrupted writes. Account device/everywhere logout revokes issuer sessions and associated login authority; remote access ends within the current lease bound.

Use native CSRF protection and fresh password verification for sensitive account mutations. Email is read-only. Display-name updates affect issuer profile only.

The isolated invitation candidate supports internal issuance, cancellation and acceptance for existing enabled local accounts. System Managers issue immutable invitations with a secret digest, local delivery address and seven-day expiry. Cancellation uses native audit history and does not change admission. Acceptance requires an unexpired server-verified link attempt bound to the browser, invitation, native session/generation and exact identity epoch. It locks and checks current inviter authority, recipient, identity and enforced policy, then saves admission, acceptance and audit atomically. A scoped in-process authorization object permits only the two exact document writes; request data cannot supply that object. Failure rolls back to a savepoint and the caller owns commit. Replaying an accepted invitation does not restore revoked admission. Passport email equality is not required. Ordinary document writes cannot accept an invitation. Separate-connection tests cover cancellation, identity change, inviter-role removal, native-session deletion and simultaneous acceptance.

Internal invitation initiation reuses native password confirmation and the existing issuer link-consent attempt. It snapshots any existing association and epoch. The signed callback confirms that exact link or creates an unapproved link, then stores verified evidence in the spent attempt with expiry bounded by the signed token. It leaves the invitation pending and does not grant admission. The raw invitation secret and local password are not sent to Passport. Ordinary linking still rejects existing links. Callback denial rolls back tentative link creation; the actual response-handler cancellation test passes.

The candidate exposes POST-only Frappe methods `passport_client.invitations.begin(name, secret, password)` and `passport_client.invitations.complete(attempt_id, secret)`. Both require CSRF, even if the site's normal CSRF check is disabled. Begin uses the existing native proof and linking policy and returns the issuer redirect with its browser cookie. Complete checks current linking policy, reads browser binding only from the cookie and performs atomic acceptance. Responses disable caching and referrers. Local HTTP tests cover a real password check, POST/CSRF/native-session/browser-cookie rejection, redirect cookies and successful acceptance through the framework transaction.

The recipient page at `/passport/invitation` uses the existing application shell and Frappe UI controls. The initial invitation URL sets a short-lived, path-scoped HttpOnly cookie and redirects to a clean URL. The initial URL still requires access-log redaction. Guests use native login. The page confirms the local password, redirects through existing issuer consent, then displays the local account and verified Frappe ID before explicit acceptance. Different email addresses are allowed. GET requests do not grant access. Acceptance requires CSRF and current server-side proof; successful acceptance clears the invitation cookie. Desktop and mobile form tests cover explicit submission and unavailable states. A complete browser journey across the site and issuer remains unverified.

Internal invitation delivery uses `invitations.issue_and_queue(user)`. It requires System Manager authority, locks the local User and reuses an unexpired pending invitation for the current delivery address. The pending lookup is a locking read so a waiting request sees the committed result even with an older transaction snapshot. New invitation creation and native Email Queue insertion share the caller's transaction; queue failure rolls back both. Frappe's scheduler, retries and Email Queue view own delivery. The helper is not whitelisted. An existing pending invitation is returned without another email; failed delivery is retried through Email Queue, while replacement requires cancellation. The invitation stores only a digest, but the restricted email queue necessarily stores the bearer link. Cancellation prevents acceptance without promising that an already queued email will not arrive.

The existing Passport Invitation Desk list provides an Invite dialog with a native User Link field and read-only delivery address. It opens the returned invitation record without claiming that mail was delivered. The document form provides View email queue and Cancel invitation; generic Save is disabled. Standard list creation shortcuts use the invitation dialog. POST methods `invitations.send_invitation(user)` and `invitations.cancel_invitation(name)` require explicit CSRF and System Manager permission. Sending also requires configured and enabled Frappe ID linking, compatible local password settings and enforced admission. Cancellation remains available independently of those linking settings. Responses expose only the invitation name. HTTP tests cover unauthorized requests, POST/CSRF enforcement, successful queue creation, repeat submission, repeat cancellation and compatibility-policy rejection. Native Desk rendering and interaction are deferred for browser verification.

Loopback SMTP tests invoke Frappe's native queue flush and stale-entry recovery functions against real queue records. They verify successful delivery, suppression of another send after recorded success, retry after a temporary SMTP rejection, terminal error and operator notification at the retry limit, recovery of a stale Sending entry, and rejection of a cancelled invitation whose email is subsequently delivered. Outgoing-account discovery uses an unsaved fixture account; transport uses real SMTP sockets to an in-memory local sink. Scheduler dispatch, external providers, TLS/authentication and the ambiguous failure after an SMTP server accepts a message but before local success is recorded remain unverified. Native queue delivery does not promise exactly-once email delivery.

Framework assumptions must be verified on the pinned baseline in [deployment](../deployment.md). Site admission, ordered connection outcomes and Pilot enrollment retain their documented owners; they do not turn Cloud team membership into application permission.
