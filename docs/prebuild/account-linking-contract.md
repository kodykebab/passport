# Existing-account linking and consent

Users may link an existing enabled site account after proving its password; no separate administrator approval is required. The site explicitly enables `passport_allow_linking`. No email matching, account creation, role changes, replacement/unlinking of existing identities or automatic admission is included.

Start at client `/passport/link` from an authenticated native local session. Refuse Guest, Administrator, federated sessions, disabled local password login and MFA policies this flow cannot satisfy. Require explicit native CSRF and fresh site-password verification with native throttling. Bind the one-use, ten-minute code/PKCE attempt to the exact local session, user and user generation. Client callback remains the registered callback; it may handle a linking attempt only in that same local session.

The issuer displays an explicit, one-use confirmation identifying the signed-in Frappe ID, registered client and callback origin, and the identity information shared. Allow and cancel are POSTs protected by native CSRF, with a short-lived durable request tied to the issuer session. Client metadata and native session are checked again on submission. Consent applies only to this linking attempt, not future applications or permissions. Cancellation returns no code. A linking grant yields an ID-token-only response with a distinct `passport-link+jwt` type, not a federated login/lease. Ordinary login cannot consume it as login evidence.

After exchanging the code, the client rechecks its enabled policy, exact native session and user generation under locks before inserting the identity. Reject an issuer subject already assigned to another user or a local account already linked to this issuer. Never overwrite an existing record. SQL uniqueness, per-user locking and a short issuer-scoped registration lock serialize competing attempts. No network requests run under the registration lock. Issuer authority is checked at token exchange; linking does not create a session, and subsequent federated login must validate current issuer authority normally. Local logout, user disablement or session replacement during the flow prevents completion.

Use official frappe-ui for the linking and consent pages; leave native password login and Desk unchanged. Keep existing login behavior for manually linked users. Test CSRF, password failures/throttling, session/user swaps, cancellation, replay, expiry, purpose confusion and concurrent conflicts using dedicated fixture accounts. No live demo identity links or credentials are changed. Unlinking, generic remembered consent, new-site provisioning and production rollout are outside this slice.
