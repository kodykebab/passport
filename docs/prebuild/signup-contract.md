# Verified issuer signup

This iteration adds `/passport/signup` for new issuer identities only. Enable it explicitly with `passport_allow_signup` on the issuer. The switch defaults off; native Frappe registration remains disabled so its separate registration API is not opened by this feature. No client-site users, roles, identity links or admission settings are provisioned. Retain the existing framework and bench.

Reuse browser-bound email challenges with an immutable `signup` purpose. Login and signup cannot consume or resend each other's challenges. Both share the existing five-per-email and twenty-per-IP hourly limits, five-minute code expiry, fifteen-minute attempt lifetime, sixty-second resend cooldown and five-failure budget. Existing addresses receive generic feedback but are never changed or re-enabled. Unknown-address login still does not create accounts. Signup is unavailable when issuer MFA is enabled.

Requesting a code creates no User or Frappe ID account. The verification form collects the code, display name and a new password. Passwords are never stored in challenge records or returned in page data. Apply native password policy and size limits. Invalid codes create nothing. After successful verification and profile validation, consume the challenge durably before native account/session work. Create a Website User with no explicit roles, no portal default-role assignment and no welcome/reset email, then create its stable Passport Account. Native User validation and creation throttling remain active. A per-address SQL registration lock serializes native User insertion; database uniqueness also prevents concurrent signup from replacing an existing account. Failed creation or a lost completion response does not make the code reusable; the user starts again or signs in if the account was created.

Successful signup records email-code authentication, uses native session creation and resumes the original allowed issuer destination. A client authorization attempt still requires its existing manual identity link and site admission. An unlinked new account is denied access to that client. Account mutations continue requiring fresh password authentication.

Use official frappe-ui controls and existing page/layout patterns. Keep password/email login available, clear inline feedback, request identifiers, resend countdowns and keyboard submission. Test policy gating, purpose separation, wrong/expired/replayed codes, existing/disabled-account preservation, concurrent duplicate creation, native password policy, partial failures and client non-admission. Use dedicated development identities and clean up only their records and sessions. Evidence stays local. Real email delivery and public production deployment remain outside this iteration's validation.
