# Email-code login — current iteration

Existing enabled accounts only, on the retained Frappe development checkout and one issuer/client. Password login remains available. Account mutations still require a fresh password. No signup, automatic identity linking, site-user creation or admission changes.

The issuer offers `/passport/email` alongside password login. Each browser attempt has its own random identifier and HttpOnly SameSite cookie; POSTs require a matching form token. Attempts in separate tabs are independent. Return navigation is limited to the issuer authorization route or account page, and never replays an application action.

Codes contain six random digits. Each code expires after five minutes; an attempt ends after fifteen minutes. Five incorrect verifications exhaust an attempt, including across resends. Resends wait sixty seconds, replace the prior code and increment its generation. Codes are stored as keyed digests with a separate site configuration key. Issuance limits are five per email and twenty per IP per hour, shared across new attempts and resends. Unknown, disabled and ineligible users receive the same public issuance response; these limits apply equally to them. Limits fail closed if Redis is unavailable.

A challenge records the user generation at issuance. Verification checks the current enabled account, email, generation and issuer authentication policy. Disabling then re-enabling an account does not revive old codes. Guest and Administrator are excluded. Email login does not bypass issuer MFA. The current Frappe ID password screen supports the seeded password-only accounts and fails closed when native authentication requires an additional step; it does not implement an MFA interface. Native IP/hour restrictions still apply.

Verification and resend serialize on User then challenge. Successful verification durably consumes the challenge before native login, because the retained framework session path commits internally. A lost response or failed session creation requires a new attempt. The native insertion hook rechecks the captured generation so disablement between consumption and session creation wins.

Native issuer sessions record authentication time and method. Password sessions use `amr=["pwd"]`; email sessions use `amr=["otp"]` and the Passport profile's `passport_auth_method="email_code"`. Clients accept only the defined matching pairs. Existing password sessions without the new marker remain password sessions. Session renewal is never fresh authentication.

Frappe Email Queue performs delivery after the challenge transaction commits. Queue creation failure leaves no usable code and returns a generic retry response. SMTP failure does not extend expiry; delayed or superseded codes remain invalid. Challenge rows contain keyed digests; request failures return generic feedback without logging submitted codes. The delivery payload necessarily contains the code in Email Queue and the recipient mailbox. Native mail-worker failure diagnostics may also capture transport context: treat queue diagnostics and local mail as sensitive development data. Hourly cleanup removes expired email challenges only. Native Email Queue records and recipients remain available for late provider callbacks; Frappe Log Settings and the configured provider own mail retention. Code expiry and generation checks remain authoritative regardless of delivery status. Passport uses the configured Frappe outgoing account or delivery-service hook, with an optional `passport_email_sender` override. Provider-neutral setup only creates the challenge digest key. Local mail capture binds only to loopback and stores captured messages outside version control.

Verification covers correct/wrong/expired/replayed codes, resend generations and budget, browser binding, independent tabs, limits, delivery failures, concurrent consumption, disablement races, authentication claims and existing password/session/lease behavior. Reports and captured messages remain local; test code is versioned.
